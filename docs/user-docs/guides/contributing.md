# Contribute with clear provenance

[English](contributing.md) | [Português](contributing.pt.md) | [Español](contributing.es.md)

Use this guide to prepare a contribution in a repository you may access. This private H02 guide is a candidate pending review/adoption. It does not grant access or rights. The organization already has a public participation route; detailed private Harness resources are optional for a contribution without the tool.

## Prepare and try it

1. Read the target repository's README, AGENTS and contribution guidance where available. Its own guidance takes precedence over organization defaults.
2. Choose an actual existing issue or use its available bug, feature or maintenance form. Describe the problem and expected result; include reproduction for a bug.
3. List original and third-party material, sources/versions, applicable terms and notices. Example: for a copied illustration without verified permission, identify the gap and request review before including it; a public URL is not permission evidence.
4. Follow the target's setup and checks. When SDD applies, review its planning stages before explicitly authorized implementation. Link the actual issue in a PR and report observed checks and missing verification.

Expected result: a reviewable proposal/contribution with provenance, scope and truthful evidence. An issue may be useful without an implementation.

## Terms, private access and recovery

The tool's terms and the destination project's contribution/license terms are separate. The [Harness terms candidate (English)](../../licensing/harness-plugin-terms.md) has owner text approval, recorded with its hash in the [approval record (English)](../../governance/h01-approval.md). It is not effective and does not yet authorize tool use. Use the actual applicable approved terms where established. If tool access/terms are unavailable, follow the target's public route without the tool or ask its owner about the missing prerequisite.

Missing rights or required review prevents acceptance. This guide creates no CLA, DCO or IP transfer. Keep vulnerability details out of ordinary public issues; use [security reporting](security-reporting.md).

Reuse [workspace setup](workspace-setup.md), [SDD](sdd-with-codex.md), [GitHub delivery](github-delivery.md) and [validation](validation-and-evaluations.md). Canonical rules: [Contribution (English)](../../../standards/core/contribution.md). Product adoption and plugin distribution each require separate evidence.
